# ADR-0006. Ток заводит собственный Vuex-стор, а не регистрирует модуль в сторе хоста

**Дата:** 2026-08-12
**Статус:** принято

## Контекст

План фазы 4 требует «Vuex-модуль: история, `conversationId`, флаги загрузки и ошибки». Обычный способ подключить такой модуль к готовому приложению — `store.registerModule('tok', module)` в сторе хоста. У этого пути в нашем случае три изъяна:

- перенос в Трансферу перестаёт быть копированием папки: нужно ещё дотянуться до её стора и занять в нём имя;
- namespace `tok` в чужом сторе — потенциальный конфликт, который выяснится только при интеграции;
- Ток перестаёт работать там, где стора у хоста нет вовсе (например, при монтировании компонента в изолированном тесте или на отдельной странице).

Состояние беседы при этом никого за пределами панели не касается: хост не читает историю сообщений и не пишет в неё.

## Решение

`TokApp` создаёт собственный экземпляр `Vuex.Store` (`createTokStore`) и раздаёт его вниз через `provide` / `inject` под ключом `tokStore`. Стор хоста Ток не трогает и `this.$store` не использует.

Внутри стора всё устроено как обычно: namespaced-модуль `conversation`, созданный фабрикой `createConversationModule({ api })` — клиент ассистента приходит извне, поэтому в тестах на его месте мок, а в Трансфере транспорт.

Следствие для компонентов: `mapState` / `mapGetters` из Vuex неприменимы — они смотрят в `this.$store`. Доступ идёт через миксин `src/tok/mixins/tokStore.js`.

## Последствия

- `<TokApp />` остаётся единственной строкой, которую хост добавляет в разметку; ничего в его сторе править не нужно.
- Vuex остаётся в списке зависимостей папки (`Vue.use(Vuex)` вызывается внутри `createTokStore`), но версия хоста используется та же — второго Vuex в бандле не появляется.
- Если однажды понадобится, чтобы Трансфера читала состояние беседы, решение придётся пересмотреть: сейчас снаружи доступны только события `open` / `close` компонента.
